# 2027 脑科学与 AI 机会雷达自动更新 PRD

- 文档状态：P1.8 自动审查、重点高校与博士资助标注已实现；5 来源抽取灰度观察中
- 版本：v0.6.0
- 建立日期：2026-08-01
- 产品对象：2027 年毕业、希望从实验心理学进入脑科学、脑机接口或 AI 交叉方向的硕士生

## 1. 背景与问题

当前站点是一份人工整理的静态快照。机会、机构、截止日期、匹配度、更新时间和行动计划都写在前端代码中。信息源变化后，页面不会主动发现、验证或更新，也不能解释一条信息何时被检查、为什么改变。

## 2. 产品目标

建设一条可追溯的机会情报管线：定期检查官方来源，保留历史快照，在不丢失最后一次可信数据的前提下更新页面，并把高风险变化送入人工审核。

### 2.1 成功指标

- 已登记来源每日自动巡检成功率不低于 95%。
- 每条公开机会展示来源链接和最后验证时间。
- 抓取失败不会导致已发布机会消失。
- 新增、截止日期改变、页面大幅变化均可追溯到一次同步运行和来源快照。
- 低风险字段自动更新；高风险字段进入审核队列。

### 2.2 非目标

- 不绕过验证码、登录、付费墙或站点访问控制。
- 不保证任意网站都能稳定解析。
- 第一阶段不让生成式模型无审核发布职业判断。
- 第一阶段不建设完整后台管理系统。

## 3. 用户故事

1. 作为求职者，我希望看到机会最后一次被官方来源验证的时间。
2. 作为求职者，我希望失效、截止或发生重大变化的机会被明确标记。
3. 作为维护者，我希望知道每次巡检检查了哪些来源、成功和失败多少条。
4. 作为维护者，我希望页面变化有原始来源、内容哈希和时间记录可复核。
5. 作为维护者，我希望系统能发现候选来源，但新域名需审核后才能成为正式来源。

## 4. 功能范围

### P0：可靠监控与动态展示

- D1 保存来源、机会、重点机构、来源快照、同步运行和审核项。
- Cloudflare Cron 每日触发来源巡检。
- 跟踪 HTTP 状态、最终 URL、ETag、Last-Modified、正文哈希和连续失败次数。
- 使用超时、有限并发和最大正文读取量保护 Worker。
- 页面通过只读 API 获取已发布机会；数据库不可用时保留静态安全降级。
- 更新时间、机会数和行动项数量由数据计算。
- Worker 输出结构化 JSON 日志，并在 D1 中保存运行摘要。

### P1：列表发现与字段抽取

- 为官方招聘/招生列表页建立按域名适配器。
- 发现候选详情页并按规范化 URL、机构、标题和年份去重。
- 抽取标题、地点、类别、截止日期与正文证据。
- 日期冲突、来源冲突、解析失败进入审核队列。
- 建立候选记录、字段证据和待发布变更的数据模型。
- 低风险字段可按策略自动合并；截止日期、批次和开放状态保持人工审核。
- 先交付 5 个试点适配器和固定网页样本回放测试，观察 7 天后扩展到全部来源。

#### P1 开发步骤

1. P1.1 数据模型：新增 candidate_records、field_evidence、change_sets，并保证迁移可回滚。
2. P1.2 适配器框架：统一列表、详情、API/RSS 的抓取与解析接口。
3. P1.3 链接发现：分页、URL 规范化、重定向归一、去重和未知域名隔离。
4. P1.4 字段抽取：标题、机构、类型、地点、批次、截止日期、开放状态和证据。
5. P1.5 变更决策：字段级比较、日期校验、冲突检测、风险分级和审核路由。
6. P1.6 灰度发布：5 个来源试点、样本回放、7 天观察，再分批扩展结构化适配器。
7. P1.7 可观察性与覆盖扩展：来源目录、逐来源日志，以及英国、爱尔兰、中国大陆、中国香港的博士/科研和企业校招入口。
8. P1.8 自动审查与重点监控：页面变化自动观察并在稳定后结案；牛津、剑桥、UCL、清华、北大等每 6 小时检查。

P1 验收门槛：试点字段抽取准确率不低于 95%，重复率低于 1%，所有公开字段可追溯到来源快照，无未经审核的高风险发布。

### P2：模型辅助与审核后台

- 生成匹配度、匹配原因和下一步建议草案。
- 提供候选来源及内容变更的批准、驳回和编辑界面。
- 支持变更通知和每周摘要。

## 5. 业务规则

- 正式来源优先级：机构官方 API/RSS > 官方列表页 > 官方详情页 > 经审核第三方。
- 抓取失败只增加失败计数，不删除机会、不清空旧字段。
- 连续三次失败创建审核项；恢复成功后清零失败计数。
- 内容哈希变化创建快照；重大变化创建审核项。
- 截止日期、招生批次和开放状态属于高风险字段，自动抽取后需规则验证。
- 新域名只能进入候选状态，人工批准后启用。
- 页面只返回 `published = true` 的机会。

## 6. 数据与审计要求

- 所有表使用 UTC 时间戳；页面按用户时区显示。
- `sync_runs` 记录触发方式、开始/结束时间、检查数、变化数和错误数。
- `source_check_logs` 记录每次运行中每个来源的结果、HTTP 状态、错误摘要及候选/证据/决策/发布计数。
- `source_snapshots` 记录内容哈希、响应状态、最终 URL 和有限长度的正文摘要。
- `review_queue` 记录审核原因、载荷、状态和处理时间。
- 页面内容哈希变化使用 `review_mode=automatic` 和 `status=observing`；下一轮哈希一致后自动结案，但不修改公开语义字段。
- 新机会、字段冲突、截止日期、开放状态和资助范围仍属于人工审核边界。
- 博士机会保存 `funding_type`、`funding_details` 与资助核验时间，区分全奖、部分资助、混合、自费和待确认。
- Worker 日志必须是结构化 JSON，不记录凭据、完整个人信息或任意响应正文。

## 7. 验收标准

- 本地迁移可创建全部数据表和初始来源/机会。
- 手动触发一次巡检后可查询到 `sync_runs` 和来源检查结果。
- `/sources` 可按关键词、博士/校招、地区、优先级和状态查询全部 47 个来源。
- `/logs` 可按来源、结果、类型、地区和 UTC 日期检索历史记录。
- 单个来源超时不会中断整批巡检。
- 304 响应不会产生重复快照。
- 页面在 D1 可用时使用数据库数据；D1 不可用时仍能渲染当前静态数据。
- `npm test`、`npm run lint`、`npx tsc --noEmit` 全部通过。

## 8. 发布与回滚

- 发布前创建 D1 数据库、填写真实 database ID、执行迁移并验证种子数量。
- Cron 初始为每日一次，观察一周后再调整频率。
- 升级 Wrangler 时推进 Compatibility Date，并执行完整 Worker/D1 回归。
- 回滚应用不会删除 D1 数据；必要时关闭 Cron，并让页面退回静态数据。

## 10. 网页入口

- `/system`：系统运行机制、实时 D1 聚合状态、自动化边界和维护动作。
- `/prd`：面向业务与研发的网页版需求、范围、规则和验收标准。
- `/sources`：当前信息源目录与采集状态筛选。
- `/logs`：历史 Cron 和逐来源采集、证据、决策、发布日志检索。
