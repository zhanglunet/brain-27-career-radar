# PRD-080/T1：本地运行方案设计（架构 + 数据主权边界）

> 对应 trend issue #390。PRD：`adopted/PRD-080-brain27-local-apply.md`。
> 借鉴：MadsLorentzen/ai-job-search（MIT，已核实）——"runs on your machine, fork it and own it"。
> 下一步：T1 确认后进 T2（岗位匹配度评估，trend #393）/ T3（申请材料定制，#395）/ T4（面试准备，#397）可并行。

打个比方：求职材料（简历、PS、套磁信）是一个人最敏感的数据，相当于"把日记交给云端陌生人批改"。本设计的核心就一句话：**日记不出机器，报纸可以上云**——公开的机会情报走云端，个人的申请材料永远留在本地。

**非目标**（PRD 要求，本设计遵守，见 §七一致性检查）：

- 不动 brain-27 云端现有架构（Workers + D1 的采集/整理/只读接口继续跑，本地助手是"延伸"不是"替换"）。
- 第一期不用云端 LLM 处理个人材料（本地模型优先；云端调用必须显式授权且可一键关闭）。
- 不做自动投递：材料准备可以 AI 辅助，投递动作永远人工。

## 一、运行形态：云端 + 本地的分工

### 1.1 架构图（文字版）

```
┌─ 云端（现有，不动）─────────────────────┐      ┌─ 本地（新增）──────────────────────────┐
│ Cloudflare Workers + D1                 │      │ brain-27 CLI（Node.js，跑在用户机器）   │
│                                         │      │                                        │
│ 采集 → 整理 → 情报库                     │      │  ① 读：机会情报（只读）                  │
│  (PRD-017 Wiki / PRD-061 自组织)         │      │  ② 存：简历/PS/背景档案（永不出机器）    │
│                                         │ 只读 │  ③ 算：Ollama 本地模型                  │
│ 只读接口：MCP / 摘要 API                 │ ────→│  ④ 产：匹配评估 → 材料草稿 → 面试准备    │
│ (PRD-018 / PRD-019)                     │ HTTPS│                                        │
│                                         │      │  落盘：~/.brain27/（SQLite）            │
└─────────────────────────────────────────┘      └────────────────────────────────────────┘
        ▲ 只写公开情报                                   ▲ 不写回云端（PRD-018 只读纪律）
        │                                                │
        └──────── 人工确认闸门（PRD-017） ────────────────┘
```

数据只向一个方向流动：**云端 → 本地**。本地永远不向云端写任何东西（评估结果、草稿、面试记录都不回写 D1）。

### 1.2 云端职责（现有链路，不动）

- 情报采集：120+ 官方信息源定时检查（Workers Cron）。
- 情报整理：Wiki 沉淀、自动归类、模糊去重、历史关联（PRD-017/061）。
- 只读服务：MCP `search_opportunities` / `upcoming_deadlines`、摘要 API（PRD-018/019）。
- 云端**不知道**本地的存在：不需要为本地助手加任何新接口（§四详述复用哪些现有接口）。

### 1.3 本地形态选型

| 候选 | 优点 | 代价 |
|---|---|---|
| **CLI（命令行）** | 零依赖分发（npx/单文件）；ai-job-search 本体就是 CLI 范式；与仓库现有 TypeScript 栈同构，可直接复用 `lib/wiki/schema.ts` 类型与 MCP 客户端逻辑；脚本化、可组合 | 非技术用户门槛高 |
| 本地 HTTP 服务（localhost） | 可被浏览器/其他工具调用，方便以后套 Web UI | 要处理端口占用、开机自启、CORS；多一个常驻进程 |
| 桌面壳（Electron/Tauri） | 体验最好 | 构建重、体积大、与"fork it and own it"的轻量精神相悖 |

**默认推荐：CLI 先行（v0.1），本地 HTTP 服务作为可选薄包装。**

理由：

1. 范式一致：ai-job-search 的走红本身就是 CLI 范式的胜利，目标用户（申博的硕士生）对终端不陌生。
2. 复用最大化：`search_opportunities` 的 MCP client、`WikiOpportunityType` 等类型定义都是现成 TS，CLI 直接 `import`，不写第二套。
3. 服务层不丢：CLI 的核心函数（评估/生成/存档）写成纯函数模块后，`brain27 serve` 一条命令就能起 localhost 服务给未来的 Web UI 用——形态是渐进的，不是二选一。
4. 桌面壳暂缓：除非 T1 待决策事项（§六-1）用户明确要，否则 v0.1 不做。

命令面（v0.1 草案，T2–T4 细化）：

```
brain27 pull [--type phd] [--region 英国]      # 从云端拉取机会情报到本地缓存（只读）
brain27 match <opportunity-id>                  # T2：匹配度评估 + 缺口分析
brain27 draft cv|ps|email <opportunity-id>       # T3：材料定制草稿（本地存档、版本化）
brain27 interview <opportunity-id>               # T4：模拟面试
brain27 status                                  # 本地数据盘点：档案/草稿/评估一览
```

## 二、数据边界表：什么上云 vs 什么绝不出机器

| # | 数据项 | 存放位置 | 上云？ | 说明 |
|---|---|---|---|---|
| 1 | 公开机会情报（title/org/type/region/funding/deadline） | 云端 D1（现有） | ✅ | 本来就是公开信息，现有链路 |
| 2 | 机会来源快照 / 审核结论 / 置信度 | 云端 D1（现有） | ✅ | 可审计性的基础，现有链路 |
| 3 | 机会关联关系（PRD-061 linking） | 云端 D1（现有） | ✅ | 公开情报的衍生数据 |
| 4 | 简历（含联系方式、身份证号等） | 本地 `~/.brain27/` | ❌ 绝不 | 最敏感数据 |
| 5 | 用户背景档案（教育/经历/技能/意向） | 本地 | ❌ 绝不 | T2 匹配的输入 |
| 6 | PS / 研究计划草稿（各版本） | 本地 | ❌ 绝不 | T3 产物，版本可追溯 |
| 7 | 套磁信草稿 | 本地 | ❌ 绝不 | T3 产物 |
| 8 | 匹配度评估结果 | 本地 | ❌ 绝不 | T2 产物；用户可手动导出分享 |
| 9 | 面试模拟对话记录 / 复盘要点 | 本地 | ❌ 绝不 | T4 产物 |
| 10 | 本地操作日志 | 本地 | ❌ 绝不 | **红线**：日志不得写入简历/材料片段（T5 专项审计） |
| 11 | 匿名使用统计 | 无（默认不采集） | 默认 ❌ | 如未来要做，必须显式 opt-in，见 §六-6 |

边界执行机制（T2–T4 落实，T5 审计）：

- **网络层**：本地助手只允许向两个云端端点发请求——MCP 只读接口与摘要 API（白名单域名）；其他出站一律拒绝。云端 LLM 调用走独立开关（§三）。
- **代码层**：`fetch` 封装统一走 `cloudRead()`（只读），不存在 `cloudWrite()`；Code Review 时以"是否存在向云端 POST 个人数据的代码路径"为红线项。
- **日志层**：`console.log` / 文件日志在写入前过脱敏函数，简历/材料字段名出现在日志即算违规（T5 审计用例覆盖）。

## 三、模型选型：本地 LLM vs 云端 LLM

### 3.1 默认推荐：Ollama 本地模型

- 选型：Ollama + 8B 级模型（如 qwen2.5:7b / llama3.1:8b，T2 时实测选定）。
- 理由：零上云、免费、离线可用；中文求职文本生成质量在 8B 级已可用（初稿+人工改写的工作流下）。
- 代价（诚实写清）：
  - 硬件门槛：8B 模型需要约 8GB 内存，M1/M2 Mac 或 16GB 内存 PC 可跑，老机器吃力。
  - 生成质量：PS 这类长文本，本地 8B 会有"AI 味"和事实幻觉风险 → T3 强制"AI 草稿，需人工改写"标注，不承诺直发可用。
  - 用户需要先装 Ollama（`brew install ollama` 一行命令；T5 的 fork 可跑通验证含此步骤）。

### 3.2 可选项：云端 LLM（默认关闭）

保留云端模型作为可选项，应对"本地模型实在写不好"的场景，但上三道锁：

1. **显式授权**：首次使用云端模型时，CLI 明确告知"将把本次输入的材料片段发送到 XXX 模型"，用户逐次确认（不是一劳永逸的开关）。
2. **一键关闭**：`brain27 config cloud-llm off` 全局关闭；关闭后相关命令降级为"只给提纲/要点"而非全文生成，功能可用、质量降级。
3. **最小发送**：只发本次任务必需的片段（如针对某机会改简历，只发该经历段落 + 机会描述），不发完整简历；发送内容记入本地审计日志（用户可查）。

### 3.3 选型对比表

| 维度 | Ollama 本地（默认） | 云端 LLM（可选） |
|---|---|---|
| 数据主权 | ✅ 个人材料零上云 | ⚠️ 需逐次授权，有审计日志 |
| 费用 | 免费 | 按 token 计费 |
| 离线可用 | ✅ | ❌ |
| 生成质量（PS/套磁信） | 中等，需人工改写 | 高 |
| 硬件要求 | 8GB+ 内存 | 无 |
| 适用场景 | 日常评估、提纲、初稿 | 终稿润色（用户主动选择） |

## 四、衔接点：本地读云端走什么接口、读什么字段

### 4.1 接口：复用 PRD-018 只读 MCP（首选）+ 摘要 API（降级）

| 接口 | 用途 | 说明 |
|---|---|---|
| `search_opportunities`（MCP） | 按 type/region/funding/keyword 拉机会清单 | 首选；本地 CLI 内嵌 MCP client（stdio/HTTP） |
| `upcoming_deadlines`（MCP） | 拉截止日，生成准备任务 | 首选 |
| 摘要 API（PRD-019） | 机会列表摘要模式 | MCP 不可用时的降级通道；token 省约 90% |
| `detail`（MCP 详情） | 单个机会下钻 | T2 评估时读完整字段 |

**不新增云端接口**：云端不知道本地的存在，现有只读接口已够用。

### 4.2 读什么字段（白名单）

机会侧（全部公开）：`id / title / org / type / region / funding / deadline / confidence / status / sources / facets.keywords / related`（PRD-061 关联）/ `detail` 下钻字段。

本地**不读**（云端本来就没有）：任何用户个人信息。云端 D1 里只有公开情报，这是数据边界天然成立的原因。

### 4.3 本地数据存哪、什么格式

- 位置：`~/.brain27/`（默认，可 `BRAIN27_HOME` 环境变量覆盖；见 §六-4 待决策）。
- 格式：**SQLite**（`better-sqlite3`，单文件 `brain27.db`），默认推荐。理由：PRD 明确要求 T3 草稿"本地存档、版本可追溯"——散落 Markdown 文件难做版本管理，SQLite 一张 `materials` 表（`id / kind / opportunity_id / version / content / created_at`）天然满足。
- 表（v0.1 草案）：
  - `profile`：用户背景档案（单行，JSON 字段）
  - `materials`：简历/PS/套磁信草稿（版本化）
  - `assessments`：匹配评估结果（`opportunity_id / score / gaps(JSON) / created_at`）
  - `interview_sessions`：面试模拟记录
  - `opportunity_cache`：云端拉取的机会缓存（只读快照，定期刷新，不可编辑）
  - `audit_log`：云端 LLM 调用审计（§三-3.2）
- 云端个人数据：**零**。`opportunity_cache` 存的是公开情报的本地副本，不算个人数据。

## 五、数据流向表（T5 审计用）

| 流向 | 内容 | 触发 | 个人数据？ |
|---|---|---|---|
| 云端 → 本地 | 机会清单/详情/截止日（MCP 只读） | `brain27 pull` / 评估时按需 | 否（公开情报） |
| 本地 → Ollama | 简历片段/机会描述（prompt） | 评估/生成时 | 是，但不出机器（localhost） |
| 本地 → 云端 LLM | 任务必需的最小片段 | 仅用户逐次确认后 | 是 → 需审计（默认关闭） |
| 本地 → 本地磁盘 | 档案/草稿/评估/面试记录 | 每次操作 | 是，不出机器 |
| 本地 → 云端 | —（无） | — | **此行必须永远为空** |

## 六、待决策事项清单（需用户拍板）

1. **本地形态**：CLI 先行（本设计默认推荐）vs 直接上桌面壳（Tauri）？桌面壳体验好但构建重，且与"fork it and own it"的轻量精神相悖。
2. **Ollama 分发**：要求用户本机装 Ollama（`brew install`，文档写清）vs 用 llama.cpp 打包进 CLI（零依赖但体积大、更新慢）？
3. **云端 LLM 默认**：默认关闭（本设计默认推荐，数据主权最干净）vs 默认开启（质量优先，但每次都要走授权流程）？
4. **本地数据目录**：`~/.brain27/`（默认推荐，用户级）vs 项目内 `./data/`（fork 后自带、换机器即走）？
5. **T2 匹配维度权重**：研究方向 / 导师匹配 / 申请条件符合度的默认权重（如 0.4/0.3/0.3）？T2 可先给初值，用户试用后调。
6. **匿名使用统计**：做不做？默认不做；如做，必须显式 opt-in 且只统计命令计数、不含任何内容。

## 八、诚实说明与风险

1. **本地模型质量差距是真实存在的**：8B 本地模型写 PS 初稿不如云端大模型，工作流按"初稿 + 人工改写"设计，不承诺直发可用。T3 的"AI 草稿"标注是强制的，不是可选项。
2. **数据边界的最大风险是"意外打破"**：比如错误日志里带出简历片段、云端 LLM 审计漏记。T5 验收含专项审计（全链路跑一遍，抓包确认个人数据零上云）。
3. **fork 可跑通依赖 Ollama**：T5 的"从零 fork 跑通"验证必须包含 Ollama 安装步骤；若用户决策 §六-2 选 llama.cpp 打包，则分发体积与更新策略另议。
4. **本设计不涉及**：云端任何改动、MCP 新接口、D1 schema 变更——这些都不需要，现有只读接口已够用。
