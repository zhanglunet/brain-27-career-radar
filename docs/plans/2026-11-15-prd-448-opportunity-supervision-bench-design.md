# 机会监督台设计草稿（PRD-448/T1）

> 来源：trend issue [#2160](https://github.com/zhanglunet/trend/issues/2160)（[PRD-448/T1] 机会监督台设计）；PRD 全文：`zhanglunet/trend` 仓库 `adopted/PRD-448-brain27-opportunity-supervision-bench.md`。
> 状态：设计草稿（T1），只开 PR 不合并，等设计评审。
> 范围：本稿只写设计、接口、数据结构与验收标准，不写实现代码，不改本仓现有代码。

## 1. 问题与目标

机会库进了假信号，会浪费投递批准门的全部人工。机会采集 agent 跑来源时，人今天只在投递批准门里看到成品：这条信号从哪个来源捞到、原始表述是什么、可信度怎么来的，全都不可见。可疑信号要等到批准那一刻才被发现。

机会监督台的目标：每一条机会信号先过监督台再进下游。信号自带采集过程，人在台上随手批注、裁决，一键把反馈发回 agent，agent 改完再回来；未点头的信号不进投递批准门；批注与反馈全程留痕。

## 2. 设计要点

### 2.1 监督对象：一条机会信号

一条机会信号是监督台上的一行记录，包含：

- 信号标识：信号 ID、产生时间、采集任务标识。
- 信号内容：机会标题、来源机构/岗位要点摘要、关键时间节点（例如截止日期）、原始链接。
- 采集过程：agent 依次跑过的来源（来源名、抓取时间、命中片段原文摘要）、去重判断、信号成型时的取舍理由，每一步带时间戳。
- 信号状态：见 2.3 的状态机。

采集过程是只读呈现：监督台展示过程，不重跑来源、不改写 agent 的结论。

### 2.2 数据模型（三件套落账）

监督台落账三类记录，缺一不可：

1. **进度记录**：信号从出炉到裁决的每一步进展（出炉、被查看、被批注、被发回、被改回、被点头/被否决），每条带时间与操作人。
2. **批注记录**：人针对信号或其某一步采集留下的批注（文本、锚定的采集步骤、批注时间、批注人）。批注只附加，不覆盖信号原文。
3. **发回反馈记录**：人一点“发回”时产生的反馈单（反馈类型：换源 / 剔除 / 补信息；反馈正文；关联的批注；发回时间）。agent 改完回来的新版本挂在同一条信号下，与旧版本并列可查，版本之间可逐项对照。

三类记录统一用信号 ID 串联；删除信号时三类记录一并归档，不单独抹除。

### 2.3 状态机与关口

信号状态流转：

```
出炉（draft）→ 待审（in-review）→ 已点头（approved）→ 进入投递批准门
                 ↓ 发回（sent-back）→ agent 改完 → 回到待审（in-review）
                 ↓ 否决（rejected）→ 归档，不进下游
```

关口规则（硬性）：

- 只有 `approved` 状态的信号可以进入投递批准门；投递批准门只审人点头过的机会。
- `sent-back` 的信号在 agent 改完回来之前不得进入投递批准门；改回来的新版本重新走待审流程，不继承上一轮的点头。
- 否决的信号不进投递批准门，只留档备查。

### 2.4 监督接入点

agent 在三个时刻向监督台交数：

1. **信号出炉时**：提交信号内容 + 完整采集过程，状态为待审。
2. **agent 改完回来时**：提交新版本 + 本轮改了什么（对照上一轮的差异摘要），状态回到待审。
3. **状态变化时**：人的每次批注、裁决、发回都实时记入进度记录。

接入方式设计为“信号事件 + 查询接口”：agent 发事件上报，监督台提供按信号、按状态、按来源、按时间查询的只读接口；监督台不直接调用 agent 内部函数。

### 2.5 批注 / 裁决 / 一键发回回路

- **批注**：人在信号详情页对任意采集步骤或整条信号写批注；批注即时保存并对同一条信号的所有查看者可见。
- **裁决**：人在信号上做三选一裁决：点头 / 发回 / 否决。裁决必须带理由（点头可留空，默认“同意信号”；发回与否决必须写理由）。
- **一键发回**：点“发回”后，批注与反馈单自动打包成一条反馈消息发回 agent；agent 侧收到的是结构化反馈（类型 + 正文 + 关联批注），不是自由文本转发。

### 2.6 呈现：监督台一屏

一屏三区：左列是待审信号清单（按出炉时间倒序，标出每条的状态、来源与等待时长）；中区是当前信号的详情（信号内容 + 采集过程步骤）；右区是批注与反馈时间线。操作集中在中区底部：批注框、点头、发回、否决四个动作。

### 2.7 与既有模块的划界

- **不管档案评审（PRD-425）**：本台不管机会档案评审过没有，只管信号出炉的全程人看没看、批没批、agent 改没改。
- **不管信号真假（PRD-379）**：本台不验信号真假，只管监督流程本身。
- **不管待办收发（PRD-365）**：本台不管收件箱的待办收发，只管未点头的信号不进投递批准门。
- **不是协同会话**：人只批注和裁决，不下场改信号内容；改信号是 agent 的事。
- **不是事后审计链**：本台是事中监督 + 反馈回 agent，不是事后留痕；留痕是监督过程的副产品。

## 3. 接口草案

| 接口 | 方向 | 输入 | 输出 |
|---|---|---|---|
| 上报信号出炉 | agent → 监督台 | 信号内容 + 采集过程 | 信号 ID、初始状态 |
| 上报改回版本 | agent → 监督台 | 信号 ID + 新版本 + 差异摘要 | 新版本号、状态回到待审 |
| 提交批注 | 人 → 监督台 | 信号 ID + 锚定步骤 + 批注文本 | 批注 ID、时间戳 |
| 裁决 | 人 → 监督台 | 信号 ID + 裁决（点头/发回/否决）+ 理由 | 新状态 |
| 一键发回 | 人 → agent（经监督台） | 信号 ID + 反馈单 | 反馈已送达回执 |
| 查询信号清单 | 监督台 → 人 | 状态/来源/时间过滤 | 信号清单 |
| 查询信号详情 | 监督台 → 人 | 信号 ID | 信号 + 过程 + 批注 + 反馈时间线 |

所有接口只传业务字段，不传真实内部主机名、IP、账号或密钥；示例一律用占位符。

## 4. 验收标准

1. 一条机会信号从出炉到点头的全程（进度、批注、发回反馈）都能在监督台上查到，缺一类记录即不通过。
2. 未点头的信号无法进入投递批准门（以关口断言覆盖：待审、发回中、已否决三种状态各至少一条反例）。
3. 发回后 agent 改回的新版本重新待审，不继承上一轮点头。
4. 批注锚定到具体采集步骤可查；反馈单包含类型、正文与关联批注。
5. 设计评审通过（T1 本身的验收标准）。

## 5. 红线

- **反爬拒绝显形、零伪装。** 监督台不改变、不掩盖采集行为的本来面目；来源拒绝采集时如实呈现拒绝状态，不伪装身份、不绕过拒绝、不把被拒的来源写成正常来源。
- **未点头的机会信号不进投递批准门。** 这是本设计的硬关口，不设例外通道、不设绕过开关。
- **人只批注和裁决，不下场改信号。** 监督台不提供直接编辑信号内容的入口。
- **文档与示例中不得出现真实内部主机名、IP、账号或密钥，一律用占位符。**
- **实现类 PR 只开不合并，等用户 review。** 本稿是设计草稿，后续 T2–T5 的实现 PR 同样只开不合并。
